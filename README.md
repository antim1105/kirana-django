# Kirana Wholesale Rate Manager — Django

A private price-tracking app for a kirana shop. Record what each wholesaler
quotes for each product, then see instantly what changed, by how much, and who
is cheapest today.

This is **not** an e-commerce site. There is no cart, no ordering and no
payment.

This is a Django port of the original React + TypeScript + Vite version.
Same screens, same rules, same look — but the data now lives in a real
database instead of the browser's `localStorage`, so it survives a cleared
cache and can be opened from the shop's phone and the back-office computer at
the same time.

---

## 1. Run it

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python manage.py migrate          # db.sqlite3 is already here; this is a no-op
python manage.py runserver        # http://127.0.0.1:8000
```

Python 3.10 or newer. Everything is stored in **`db.sqlite3`**, the file
sitting next to `manage.py`. It ships already migrated and empty, so the four
commands above are the whole install and there is no database server to
configure. Run `migrate` anyway out of habit — it just confirms the schema is
current.

**The app starts completely empty.** No sample products, no preset
categories. The first screen asks you to add a product. To see the comparison
features working without typing anything:

```bash
python manage.py load_demo_data   # 20 products, 5 wholesalers, 3 weeks of rates
python manage.py clear_data       # back to empty
```

Both are also buttons on the Settings page.

Other useful commands:

```bash
python manage.py test                     # 108 tests
python manage.py createsuperuser          # then visit /admin/
python manage.py collectstatic            # before deploying
```

Nothing is compiled. There is no `npm install`, no bundler and no build step:
Tailwind's utility classes come from its CDN script, the component classes are
plain CSS in `app.css`, and the price chart is SVG generated by the template.

## 3. How the data is stored

Everything lives in one file: **`db.sqlite3`** in the project directory. That
single file *is* your shop's data — back it up by copying it, move the app to
a new machine by carrying it across. Point it somewhere else with
`SQLITE_PATH` (a relative value is resolved against the project directory):

```bash
export SQLITE_PATH=/srv/kirana/rates.sqlite3
```

Three SQLite pragmas are set on every connection, in `config/settings.py`:

| Pragma | Why |
| --- | --- |
| `journal_mode=WAL` | The shop can read on a phone while a rate is being saved on the desktop, instead of one blocking the other. |
| `foreign_keys=ON` | SQLite only enforces foreign keys when asked, and deleting a product relies on the cascade to its rates and purchases. |
| `synchronous=NORMAL` | Fast writes that are still safe against an app crash. |

WAL mode creates `db.sqlite3-wal` and `db.sqlite3-shm` alongside the main
file. They are normal, and SQLite folds them back in when the last connection
closes — but if you copy the database while the server is running, **copy all
three**, or use `sqlite3 db.sqlite3 ".backup backup.sqlite3"`, which is safe
at any time.

SQLite is a real database and comfortably handles a shop's volume — tens of
thousands of rates is nothing to it. Section 3.1 covers moving to PostgreSQL
or MySQL if you ever want several people writing at once from different
locations.

Six tables, mirroring the TypeScript interfaces they came from:

| Table | Holds | Notes |
| --- | --- | --- |
| `manager_product` | what you buy | name is unique |
| `manager_wholesaler` | who you buy from | company name identifies them |
| `manager_rate` | a quote, one per product/wholesaler/day | `effective_rate` computed on save |
| `manager_purchase` | an actual buy | `total_amount`, `final_amount` computed on save |
| `manager_category` | categories you have typed | remembered for suggestions |
| `manager_shopsettings` | one row: shop name, currency, date format | replaces the settings key |

Money is `DecimalField`, never float — these are rupee amounts, so two-place
rounding has to be exact rather than approximately right.

The three formulas from the original are enforced in `Model.save()`, not in a
view, so they hold whatever writes to the database — a form, the admin, the
CSV importer or a future API:

```
effective_rate = purchase_rate + (transport_cost + other_cost) / quantity
total_amount   = quantity * rate
final_amount   = total_amount + transport_cost + other_cost
```

Deleting a product deletes its rates and purchases (`on_delete=CASCADE`), and
the confirmation page tells you exactly how many rows will go. Same for a
wholesaler.

### 3.1 Switching to PostgreSQL or MySQL

Set two environment variables and re-run `migrate`. No code changes:

```bash
export DATABASE_ENGINE=postgresql
export DATABASE_NAME=kirana DATABASE_USER=kirana DATABASE_PASSWORD=secret
pip install "psycopg[binary]"
python manage.py migrate
```

To move existing data across, export a backup from **Reports → Download a
backup** first, switch the database, then restore it from **Settings →
Restore a JSON backup**. The backup references products and wholesalers by
name rather than by id, so it loads into an empty database cleanly.

## 4. How to add a new product

1. Open **Products** and press **Add product**.
2. Name, category and unit are required. Brand, pack size, minimum stock and
   notes are optional.
3. **Category and unit are open text fields, not fixed dropdowns.** Type
   whatever you use — "Dry fruits", "Pooja items", "quintal", "peti", "bori".
   Anything you have used before is suggested as you type, but you are never
   limited to a list. A new category is saved automatically and appears in the
   Products filter and on the next product you add.
4. There is no limit on how many products you add.

Unit matters most: every rate is recorded per that unit, and the rate form
picks it up automatically once you choose the product.

Duplicate names are rejected, case-insensitively, so "Sugar" and "sugar"
cannot both exist.

## 5. How to add wholesale rates

Open **Add rate**. The panel beside the form shows, as you type, the
**previous rate** (from the same wholesaler if there is one, otherwise the
newest from anyone), the **movement** in rupees and percent, the **effective
rate**, and who currently has the lowest price for that product.

Pressing **Review and save** shows a full summary — and saves nothing yet.
The second press writes it. If a rate for the same **product + wholesaler +
date** already exists, that review screen becomes a warning with three
choices: **Update the existing one**, **Create a second entry**, or go back
and edit.

That two-step flow is this port's version of the original's confirmation
modal. It was done with pages rather than a dialog for a reason: a modal
holding a form does not survive a page reload or the browser's back button on
a server-rendered app, and the review screen works with JavaScript switched
off entirely.

The live preview panel is the one thing that does use JavaScript, through a
small JSON endpoint at `/api/rate-preview/`. Block it and the same figures
still appear on the review screen — nothing is lost but a round trip.

## 6. How comparison works

All of it sits in `services/analytics.py` as functions that take ids and
return dataclasses:

- `difference = current_rate − previous_rate`
- `percentage_change = ((current − previous) / previous) × 100`
- Green means the rate came down, red means it went up, grey means no change.
  Movements below 0.0001 count as no change.

Five views use it:

- **Dashboard** — `latest_changes()` compares each product's newest rate with
  the one before it, then groups into costlier / cheaper / unchanged.
- **Rate history** — `rate_history()` walks one product's rates newest-first
  and compares each row with the row beneath, filtered by wholesaler,
  movement and date range, with an SVG price chart beside it.
- **Compare → two dates** — `compare_dates()` takes the latest rate recorded
  *on or before* each date, so a date with no entry still resolves.
- **Compare → wholesalers** — `wholesaler_quotes()` takes the newest quote
  from each wholesaler, sorts ascending and marks the cheapest. Ties share
  the badge.
- **Reports** — reuses the same functions for the rate-change report and the
  monthly totals.

Two details that are easy to get wrong, and are covered by tests:

- Two quotes recorded on the **same date** keep the order they were entered,
  so "previous" means the one you typed before, not an arbitrary row.
- A rate that is the first of a month is still compared against the last rate
  of the previous month, so a monthly report does not show every product
  starting from scratch.

## 7. Where the work happens

Reads go to SQL where SQL is the clearer tool — `spend_by_wholesaler` is a
`GROUP BY`, `rate_on_date` is `WHERE date <= ? ORDER BY date DESC LIMIT 1`.
Positional comparisons ("this rate against the one below it") stay in Python;
window functions could do them, but not more readably at a kirana shop's data
size. If the tables ever grow past that, `latest_changes` and `rate_history`
are the two functions to rewrite, and both are covered by tests that do not
care how they are implemented.

## 8. Deploying

```bash
export DJANGO_DEBUG=False
export DJANGO_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(50))')"
export DJANGO_ALLOWED_HOSTS=rates.myshop.in
export REQUIRE_LOGIN=True

pip install gunicorn
python manage.py migrate
python manage.py collectstatic --no-input
python manage.py createsuperuser
gunicorn config.wsgi --bind 0.0.0.0:8000
```

With `DJANGO_DEBUG=False` the security settings switch on automatically, and
with `REQUIRE_LOGIN=True` every page sits behind the login screen. Set
`DJANGO_SECURE_SSL_REDIRECT=True` once a certificate is in place.

One thing to change if you put this on the public internet: the Tailwind CDN
script in `templates/manager/base.html` is fine for a shop's own machine or a
small internal server, but for a public deployment install Tailwind properly
and build a stylesheet, so the app does not depend on a third-party CDN being
up.
